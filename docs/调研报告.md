## 二、QQ 机器人生态现状（2026）

### 2.1 2026 年的关键变化

1. **旧协议路线已死**。go-cqhttp 依赖的 MiraiGo 旧协议早就不被新版 QQ 接受，项目最后一次代码提交在 **2024-05-09**，最后一个 release 是 **2023-10-09 的 v1.2.0**。它仍是 star 破万的「经典项目」，但已经不能用于当前 QQ 版本。
2. **现在的主流是驱动官方 NTQQ 客户端**。代表是 NapCatQQ、LuckyLilliaBot（原 LLOneBot）、Lagrange.Core。它们的共同点是：跟着官方客户端更新，用官方客户端登录（所以能扫码、能过验证），再对外暴露 OneBot 等标准协议。
3. **协议侧在分裂**：Lagrange.Core 的 V2 主推自研 **Milky** 协议，并把 OneBot v1 放进了已 sunset 的 `v1` 分支；LuckyLilliaBot 同时支持 OneBot 11 / Satori / Milky；NapCat 以 OneBot v11 为主，兼容多种接口。**OneBot v11 仍是生态兼容性最好的选择**，把它当作应用层与协议端之间的稳定边界最省心。
4. **框架层的重心转向 LLM**。AstrBot（46,664★）、LangBot（18,901★）本质都是「接入大模型的机器人框架」，把模型、记忆、插件、WebUI 打包好了，适合开箱即用；NoneBot2（7,787★）保持「轻框架 + 自己写插件」的路线。

## 三、「大肥鱼」到底是什么？

### 3.1 结论

**「大肥鱼」不是任何框架的名字**，而是 DeepSeek 官方蓝色鲸鱼 logo 的社区二创形象——一条蓝色鲸鱼娘，网友管它叫「大肥鱼」「鲸鱼娘」。在 GitHub 上：

- 中文搜索 `dafeiyu`、英文 `fatfish` 都能搜到大量人类/项目，但它们的共同点是**把「大肥鱼」当角色名**，不是当技术名词；
- 没有名为 `dafeiyu` 的框架、SDK、协议或库；
- 反而有专门「清理大肥鱼」的浏览器插件，说明它是**到处出现的机器人人格/形象**，而不是某个具体实现。

因此，本项目的正确做法是：**「大肥鱼」只作为机器人的人设名**，技术底座仍然要按选型结论来挑（最终定为 NapCat + AstrBot + DeepSeek，见 4.0）。

- 「大肥鱼」这个词在社区已经泛化成**人格/形象**，同一个名字下面有 QQ 机器人、桌宠、直播系统、学习平台，甚至清理工具。这进一步说明它是**角色名，不是框架名**。

## 四、选型结论与理由

> ### ⚠️ 4.0 定稿更新（2026-11-11，以此为准）
>
> 下列 4.1~4.3 是**调研阶段的初始推荐**（NoneBot2 自研插件），保留作为对照。
> 用户随后冻结了技术栈，**最终交付路线改为**：
>
> ```
> QQ 小号 ──► NapCatQQ（协议端）──► AstrBot（机器人框架）──► DeepSeek API（deepseek-chat）
> ```
>
> - **为什么改**：目标是「开箱即用、图形化配置」，AstrBot 的 WebUI 能直接管平台、Provider、人格、记忆，不用写代码；代价是 AGPL-3.0 与封装较重。
> - **实测结果**：这条链路在我们这里跑通了离线全链路（反向 WS 握手、私聊回复、群 @ 回复、多轮记忆、人格注入），DeepSeek 端点可达性由 401 证明，详见 [`实测记录.md`](实测记录.md) 第 0 节。
> - **对 4.2 结论的影响**：4.2 第 4 条「可控性」是当初选 NoneBot2 的核心理由；用户明确更看重省事，因此该条不再成立。其余活跃度 / 部署 / 稳定性结论不变。
> - **交付物**：`astrbot/compose.yml`、`astrbot/persona_dafeiyu.txt`、[`上手说明.md`](上手说明.md)。
> - NoneBot2 自研版本（`bot.py` + `dafeiyu/`）保留在仓库中，作为可独立运行的对照实现，不再是主线。

### 4.1 选定组合（调研阶段，已被 4.0 取代）

```
NapCatQQ（协议端）─OneBot v11 反向 WS→ NoneBot2 + adapter-onebot（应用层）
                                      └→ 自研 dafeiyu 插件 → DeepSeek（deepseek-chat）
```

### 4.2 为什么是这套

1. **活跃度**：NapCat 2026-11-10 有提交、2026-10 有 release；NoneBot2 与 adapter-onebot 均在 2026-11-10 有提交。链路中没有停更组件。
   （对照：go-cqhttp 代码停在 2024-05，Lagrange 的 OneBot v1 已 sunset。）
2. **部署难度**：NapCat 下载解压、WebUI 扫码即可；本项目 `pip install -r requirements.txt` + `python bot.py`。用户只需做两件手工事：填 Key、扫码。
3. **稳定性**：NapCat 跟着官方 NTQQ 走，是目前唯一被大规模使用、能稳定登录 2026 年 QQ 的协议端；OneBot v11 兼容性最好，换协议端（比如改用 LuckyLilliaBot）时应用层几乎不用改。
4. **可控性**：需求明确要求「人设可配置、密钥只能走配置、多轮记忆」，用 NoneBot2 写自己的插件，所有行为都在本仓库几百行 Python 里，改和排查都直观。AstrBot 虽更省事（46,664★），但逻辑封装在框架内、且是 AGPL-3.0。
5. **生态印证**：社区里的同类「大肥鱼」QQ 机器人几乎全是 `DeepSeek + NapCat/OneBot 11` 组合，说明这条路线是当前的主流实践。

### 4.3 什么情况下应该换方案

| 你的诉求 | 更合适的方案 |
| --- | --- |
| 完全不想写代码，图形化配完就用 | AstrBot + NapCat（另有现成 `dafeiyu-astrbot` 整合） |
| 需要知识库/客服问答、多平台（微信/飞书等） | LangBot |
| 偏好 TypeScript，喜欢插件市场与控制台 | Koishi + NapCat |
| 想用 Milky/Satori 新协议 | LuckyLilliaBot 或 Lagrange.Core + 对应适配器 |

## 五、交付与验证摘要

- 代码：`bot.py` + `dafeiyu/`（配置、记忆、DeepSeek 客户端、回复引擎、插件入口），密钥零硬编码，`.env*` 已 gitignore。
- 验证：26 个单元测试全部通过；`scripts/e2e_mock.py` 启动真实 NoneBot 并用假 NapCat 通过真实 WebSocket 验证了**私聊回复、群聊不 @ 不回、群聊 @ 回复（带 @ 提问者）、触发词触发、多轮上下文**五条链路；`bot.py` 可正常启动并挂载 OneBot v11 适配器。
- **未做真实 QQ 扫码登录**：需要用户本人的 QQ 账号与手机，属正常边界。
- **未做真实 DeepSeek 调用**：当前环境没有可用 Key，`--real` 模式已确认会给出「未配置 DeepSeek API Key」的友好提示。填入 Key 后运行 `python scripts/selfcheck.py --call` 即可验证真实调用。

## 六、留给用户的两步

1. **填 Key**：`cp .env.example .env`，在 `DAFEIYU_DEEPSEEK_API_KEY=` 后填入 <https://platform.deepseek.com/api_keys> 创建的 Key，然后 `python scripts/selfcheck.py --call` 验证。
2. **扫码登录 QQ**：安装 NapCatQQ → 打开 WebUI（默认 6099 端口）→ 扫码 → 新建反向 WebSocket 客户端，地址 `ws://127.0.0.1:8080/onebot/v11/ws` → 先 `python bot.py` 再启用连接。

详细步骤、常见问题见 [README](../README.md)。
