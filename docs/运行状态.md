### 4.5 身份锚点升级 + 三层记忆（2026-11-11 20:40）

**为什么要再做一层**：AstrBot 自带的 `identifier` 只写 `User ID/Nickname`，没有 unified_id，也没有任何「记忆」能力；`agent_runner` 自带的压缩只在 token 超限时触发（`max_turns=-1`，即不按轮封顶），上下文条数会随聊天时长一直涨。本节把它补齐。

#### 4.5.1 身份锚点

插件 `astrbot_plugin_aling_memory` 在 `on_llm_request` 里找到那条消息末尾的 `<system_reminder>`，**追加一行**（不新建块、不刷屏）：

```
身份锚点(unified_id): napcat:GroupMessage:555111 | platform_id=333444 | 显示名=阿哲 | 群聊 群号 555111；
本会话里「333444」是唯一稳定身份，昵称可能变化或重名
```

- `platform_id` 就是 QQ 号（aiocqhttp 的 `sender.user_id`），**唯一稳定**；
- `unified_id` 用的是 AstrBot 的 `unified_msg_origin`（`平台:消息类型:会话`）——4.29.4 源码里没有叫 `unified_id` 的字段，这里把它和 QQ 号一起写进同一行，形成「平台会话 + QQ 号」的映射；
- 昵称/群名片只作 `显示名` 展示，不参与认人；
- 这段随消息落库，之后翻历史仍能看到是谁说的：`evidence/identity_anchor_context.log`（从 `conversations` 表扒出的原文，两个 QQ 号各一条）。

人设里的【认人】段落也同步改成按 QQ 号（**注意：22:30 起已进一步改为「内部按 QQ 号、对外只念昵称」，见 §4.5.1b，下面的 620 字旧版仅作记录**）：`astrbot/persona_aling.txt` 与 DB `personas` 行 `aling` 均为 620 字，原来的 422 字角色卡一字未动，只替换了末尾那一段：

```
【认人】
群里是好几个人一起说话，每条消息都带着发送者的 QQ 号（User ID / platform_id，还有 unified_id 那串），昵称和群名片只是显示名，会改、会重名，别拿它当人。认人就认那串数字：不同 QQ 号说的话分开记，别把甲的事算到乙头上；同一个人换了昵称，也还是他。有人自报名字就记成「QQ号 → 名字」，再叫错就是你自己笨。真认不出来就直说"你是谁啊"，别瞎猜。
```

#### 4.5.1b 称呼只用昵称：QQ 号锁在内部（2026-11-11 22:30）

**问题**：标识里带着 QQ 号，模型有几率把它念出来（群里出现「<你的管理员QQ号> 你刚说什么」），很出戏。

**原则**：QQ 号只做**内部身份锚点**（记忆归档、跨会话识别不变），**机器人发出去的任何一句话里都不出现**；称呼人一律用昵称/群名片。

**改了三处**：

| 位置 | 改什么 | 回滚 |
| --- | --- | --- |
| `astrbot/persona_aling.txt` 的【认人】段（DB `personas.aling` 同步，620 → 813 字） | 明确「编号只准在心里记，不许说出口；称呼一律用昵称/群名片；看不出是谁就直接问，不报数字；讲故事转述也一样」 | 用备份 `backup/nickname_<时间戳>/persona_aling.txt` 覆盖回去，再跑 `scripts/bootstrap_aling.py` 写库 |

#### 4.5.2 选型：为什么是自研插件

调研时间 2026-11-11，数据以当时各仓库 README/metadata 为准（星标和版本会变）：

#### 4.5.5 已知限制

- **短期封顶是"轮"不是"token"**：一轮很长时仍可能顶到模型窗口；需靠 provider 侧 `max_context_tokens` 兜底。
- **中期摘要是 LLM 写的**，可能漏细节/写错人称；因为群聊上下文是共享的一份（这是既定行为），摘要是**群级**的，不会按人拆。
- **长期事实的抽取质量取决于模型**：会偶尔抽出「空调开到十六度」这类弱事实，也会把一次性的闲聊记下来；已有相似去重和「宁缺毋滥」提示词，但不是 100% 干净。
- **每轮多一次 LLM 调用**（`long_term_extract_every_turns=1`）；想省额度可改成 2~3，代价是最近一两轮的事可能还没入库。
- **QQ 号来源**是 aiocqhttp 的 `sender.user_id`，mock 与真实群字段一致；未用两个真实 QQ 号在真实群里做端到端验证（我不代发真实消息）。
- 插件的记忆库是独立 SQLite（`data/plugin_data/astrbot_plugin_aling_memory/memory.db`），`/reset` 只清 AstrBot 会话，不清长期条目（这是有意为之）。

### 4.7 分条说话：把一段回复拆成多条消息（2026-11-11 21:30）

**改前现状（`evidence/current_single_message.log`）**：一条 100+ 字的回复被 AstrBot 作为**一帧** `send_private_msg` 发出（`captured 1 send_* frame`），模型输出里的空行和句子全塞在同一条里。成形链路是：

```
LLM 完整输出 → result（一条 MessageChain，单个 Plain 段）
  → ResultDecorateStage.process（result_decorate/stage.py:209 起：可选分链）
  → RespondStage（respond/stage.py:353 起：逐个 comp 调 event.send + 间隔 sleep）
  → aiocqhttp → NapCat send_msg
```

**选型：用 AstrBot 4.29.4 自带的 `platform_settings.segmented_reply`**（`core/config/default.py:110`，默认 `enable=false`）。它正好在 result_decorate 按正则把 Plain 拆成多个 `Plain` 段（非 Plain 的 At/Reply/Image 原样保留、不拆），再由 respond 逐条 `event.send()` 并 `asyncio.sleep(interval)`——正是要的效果，零插件、零额外依赖、零额外 LLM 调用。

> 市场里确实有分段插件（`astrbot_plugin_splitter` 54★、`astrbot_plugin_smart_segmentation`、`astrbot_plugin_smart_segment_reply` 等，见市场数据 `2026-11-11T13:03Z` 快照），但内置功能已覆盖需求，再装插件只会多一层维护和冲突面，故不用。

**改动（两处，都在既有配置文件里）**：

| 文件 | 改前 | 改后 |
| --- | --- | --- |
| `data/astrbot/cmd_config.json` → `platform_settings.segmented_reply` | `enable=false`，regex `.*?[。？！~…]+\|.+$`，interval `1.5,3.5`，阈值 150 | `enable=true`，`interval="0.5,1.2"`，`words_count_threshold=500`，regex `(?s).*?\n{2,}\|.*?[。？！]+\|.+$` |
| 同文件 `platform_settings.ignore_bot_self_message` | `false` | `true`（纵深防御：万一同号被 NapCat 回传，不把自己发的消息当新输入） |
| `persona_aling.txt` + DB `personas.system_prompt`（`aling`） | 620 字 | 714 字：**只新增一段【分条】**，其余角色卡一字未动 |

参数理由：
- **先按空行切，再按 `。？！` 切**——阿凌的动作描写本身就用空行分段（`*掀被子*` / 台词 / `*别过脸*`），所以「动作一条、台词一条」天然像人；句中的 `…`、`~`、`？`、`？！` 不再触发切分，避免把一句话拦腰截断（默认 regex 里带 `|` 和 `~`，会把 `https://a.com/?b=1` 这类链接切碎）。
- **间隔 0.5~1.2s**：比默认 1.5~3.5s 短得多，11 条的长回复也只要 15s 发完。
- **阈值 500 字**：内置逻辑是「`len(text) > threshold` 就整体直发」，阈值太低会把长文整条发出（反而不像人）；500 字对 2~3 秒的 DeepSeek 回复足够。
- **`ignore_bot_self_message`**：本部署机器人号与「管理员号」不同，NapCat 的 `reportSelfMessage` 也是 `false`，这条属于双保险。

**拆分正确性自检（`evidence/segmented_split_cases.log`，exit=0）**：普通两句+动作 → 3 条；含 URL 的一句 → 1 条（链接完整）；`那个……我、我才没有等你。` → 1 条（省略号不拆）；`真的假的？！你再说一遍！` → 2 条；多句长回复 → 4 条。拼回去与原文逐字一致，`integrity_bad = 0`。

## 八、如实说明：限制与不确定项

| 项目 | 结论 | 依据 |
| --- | --- | --- |
| 容器会随本次任务/会话结束被回收吗 | **不会**（本机范围内） | 容器在 `/system.slice/docker-*.scope`，与会话的 `user.slice/session-165.scope` 分离；PID 1 为 systemd，`docker.service` active + `Restart=always`；容器 `restart: unless-stopped` |
| 平台层面整机被回收 | **不确定** | 取决于运行环境提供方，本机内无法验证 |
| 6099 / 6185 外网可达 | **不能** | `ss -ltnp` 显示只监听 `127.0.0.1`；公网 IP 直连超时。需要 SSH 转发：`ssh -L 6099:127.0.0.1:6099 -L 6185:127.0.0.1:6185 用户@主机` |
| 容器「healthy」 | 不能这么说 | compose 无 HEALTHCHECK，只能证明进程在跑、日志无致命错误、端口在监听 |
| 真机 QQ 收发 | 未由我测试 | 机器人已登录，但我不会用你的号向外发消息；需要你亲自发一条 |
| 一次私聊表情消息未回复 | 观察现象，未定性 | 18:35:38 收到 `[表情:484]` 后日志无「Prepare to send」；推测为纯表情无文本、不构成有效提问，未深入验证 |
| 标识格式可否只显示昵称 | **不能**（4.29.4） | 格式写死在 `astr_main_agent.py`，WebUI 无此选项；且 aiocqhttp 用 `card or nickname`，群名片优先；QQ 号依赖插件额外追加的那一行 |
| 三层记忆的「短期封顶」是否等同 token 封顶 | **不是** | 按轮数封顶（默认 12 轮），超长单轮仍可能顶模型窗口，需要 provider 的 `max_context_tokens` 兜底 |
| 认人能力用两个真实 QQ 号验证 | 未做 | 我不用你的号向群里发测试消息；用 mock NapCat 以两个不同 user_id/nickname 走**真实 WS + 真实 DeepSeek**，并核对了真实群已有的标识字段 |
| 三层记忆的「新开会话」 | 用新群号模拟 | 同一 QQ 号在新群号（新 `umo`）里仍能取到长期条目、但拿不到上一个群的上下文；这与「私聊/群聊上下文隔离」的既定行为一致，不是新增改动 |
| 管理员用真实 QQ 号 <你的管理员QQ号> 实测 | **未做** | 我没有使用你的 QQ 号向任何会话发消息；验证走 mock NapCat，以 `user_id=<你的管理员QQ号>` 走**真实 WS、真实鉴权代码、真实日志**，管理身份判定与真号完全同一条分支（`str(sender_id) == admin_id`）。你用真号私聊 `/provider` 可自行复核 |
| 管理员能不能在 WebUI 里改配置/装插件 | 未纳入本次范围 | 那是 WebUI 后台账号（`astrbot`）的权限，与 `admins_id`（QQ 号）无关；本次只按官方方式配了 QQ 管理员。WebUI 密码仍是初始值，建议尽快改 |
