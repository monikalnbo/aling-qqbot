# QQ 机器人方案选型对比

> 数据采集时间：**2026-11-11**，全部来自 GitHub API（`gh api repos/<owner>/<repo>`）与 `gh search repos` 实时查询，非记忆、非猜测。
> 复现命令见文末。星数会变，结论以「活跃度 + 是否支持当前 QQ + 部署难度 + 稳定性」综合判断，而不是只看 star。

## 一、两条技术链路先分清

QQ 机器人不是一个软件能搞定的，它分两层：

1. **协议端（协议实现）**：真正登录 QQ、收发消息的那一层。2026 年主流做法是驱动**官方 NTQQ 客户端**（NapCat / LLOneBot / Lagrange.Core）或已被淘汰的旧协议（go-cqhttp 用的 MiraiGo）。
2. **机器人框架（应用层）**：接协议端的事件，写业务逻辑、接大模型。NoneBot2 / Koishi / AstrBot / LangBot 属于这一层。

所以「选型」必须是**协议端 + 框架 + 大模型接入**三件套的组合，不能单拎一个项目比。

要点：

- **go-cqhttp 确认已停维**：最后一次提交 2024-05-09，最后一个 release 停在 2023-10-09。网上大量老教程还在用它，2026 年照抄会直接登录失败。
- **Lagrange.Core 的 OneBot v1 已 sunset**（README 明确写 "For V1 that has sunset"），现在主推自家的 Milky 协议；用 OneBot v11 生态要额外转换，得不偿失。
- **LLOneBot 改名 LuckyLilliaBot**，仍在活跃（2026-11-11 有提交），但它是 QQNT 插件形态，要先给 QQ 装 LiteLoaderQQNT，对非技术用户门槛更高。
- **NapCat** 是当前事实标准：star 最高、日更级活跃、带 WebUI 图形界面扫码登录、文档齐全，还被 AstrBot 官方 README 点名推荐。

> `chatgpt-on-qq`：**GitHub 上没有以此为主流项目名的框架**。`gh search repos "chatgpt on qq"` 结果都是个人小插件/玩具（最高 51 star，2024-04 停更）。它是一类「把 ChatGPT 接进 QQ」的教程叫法，不是可选的框架。

框架侧结论：

- **AstrBot** star 最多、最省事，如果目标是「立刻能用、不想写代码」，它是第一选择；代价是 AGPL-3.0、逻辑藏在框架里，想定制人设/记忆策略要顺着它的插件体系走。
- **LangBot** 强在知识库和多平台接入，对「一只陪我聊天的鲸鱼娘」属于杀鸡用牛刀。
- **Koishi** 的图形化最好，但需要 Node 生态知识，且要改逻辑得写 TS。
- **NoneBot2** 代码全在自己手里、Python 可读性最好、OneBot v11 适配器活跃。对一个需要「人设可改、记忆策略明确、密钥严格走配置」的定制机器人，它最合适——所有行为都能在几百行里看明白。

## 四、最终选型（推荐组合）

> ### ⚠️ 定稿：技术栈已冻结为 AstrBot
>
> 本章 4 节是**调研阶段的推荐**（NoneBot2 自研插件）。用户随后拍板，**最终交付路线为**：
>
> ```
> QQ 小号 ──► NapCatQQ ──OneBot v11 反向 WS──► AstrBot ──► DeepSeek（deepseek-chat）
> ```
>
> 上表中 AstrBot 的劣势（AGPL-3.0、封装重）在「要省事、图形化配置」的目标下可以接受；
> 其优势（46,664★、开箱即用、WebUI 直接管平台/provider/人格/记忆）成为决定性因素。
> 该路线已实测跑通（见 [`实测记录.md`](实测记录.md) 第 0 节），完整步骤见 [`上手说明.md`](上手说明.md)。
> 下文 NoneBot2 方案保留作为对照实现。

```
NapCatQQ（协议端，扫码登录 QQ）
   └─ OneBot v11 反向 WebSocket
        └─ NoneBot2 + nonebot-adapter-onebot（应用层）
             └─ 自研「大肥鱼」插件 ──► DeepSeek 官方 API（deepseek-chat）
```

理由：

| 维度 | 说明 |
| --- | --- |
| **活跃度** | NapCat 2026-11-10 仍在提交、v4.18.42 是 2026-10 的 release；NoneBot2 2026-11-10 有提交，适配器同步维护。整条链路没有停更组件。 |
| **部署难度** | NapCat 解压即用 + WebUI 扫码；NoneBot2 一条 `pip install -r requirements.txt` + `python bot.py`。全程只有「填 Key、扫码」两个手工动作，非技术用户也能照 README 走完。 |
| **稳定性** | NapCat 基于官方 NTQQ，跟着官方客户端更新，是目前唯一在 2026 年还被大规模使用的协议端方案；OneBot v11 是事实标准，生态最全；go-cqhttp 已死、Lagrange OneBot v1 已 sunset，都不再是「稳」的选项。 |
| **可维护性** | NoneBot2 插件模式让「大肥鱼」的行为、记忆、错误处理全是本仓库里可读的 Python，改人设只动 `config/persona.txt`，不需要碰框架源码。 |
| **合规与授权** | NoneBot2 为 MIT；NapCat 为混合协议开源（使用前阅读其 License）。相比之下 AstrBot 为 AGPL-3.0，二次分发有额外义务。 |

**没有选 AstrBot 的原因**：它确实更省事，但本项目要求「人设提示词写在配置里可改、多轮记忆策略明确、密钥只走配置」，还要能逐行讲清楚逻辑。AstrBot 的封装会让这些变成「在框架里找地方配」，定制和排错成本反而更高。如果你只想最省事，用 AstrBot + NapCat 也是完全合理的路线（社区已有 `whyever77/dafeiyu-astrbot` 这类现成整合，见调研报告）。

# 框架
gh api repos/nonebot/nonebot2 --jq '.stargazers_count, .pushed_at, .license.spdx_id'
gh api repos/nonebot/nonebot2/releases/latest --jq '.tag_name, .published_at'

gh api repos/koishijs/koishi --jq '.stargazers_count, .pushed_at'

# chatgpt-on-qq 是否存在主流项目
gh search repos "chatgpt on qq" --limit 10 --json fullName,stargazersCount,pushedAt
```

> 说明：`pushed_at` 会被分支、fork 同步等操作刷新，判断「是否停维」要看 **默认分支最后一次 commit 时间** 和 **最新 release 时间**。go-cqhttp 就是典型例子：`pushed_at` 显示 2026-10-20，但真实代码提交停在 2024-05-09，release 停在 2023-10-09。
